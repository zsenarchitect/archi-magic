# Batch duplicate Revit views with reviewed names and templates (#143)

Base 0c523067c4313bd9e8c3898be4ffd32d874463d7. GitHub #143 asks for plain, with-detailing and dependent copies, a view template and a naming pattern. The acceptance criterion is exact new names without automatic suffixes. There is no duplicate-view recipe in am-safe-change/SKILL.md:10–24. Its focus-view recipe provides a verified creation and Keep/Discard workflow (skills/am-safe-change/recipes/focus-view.md:5–12).

1. Read a bounded explicit list of host view IDs and one template ID. Bind the saved document to project UID and path digest, with view and template IDs and UIDs. Read source names, view types, current template IDs, primary/dependent relationships, template compatibility and duplicability for each requested native option. Read the project view-name inventory and existing dependent families touched by the request. Include sheet placements for existing affected views and template-controlled parameter identifiers. Reject incomplete inventory and cross-document inputs.
2. Use explicit `plain`, `detailing`, or `dependent` for each source. Expand a literal naming pattern using only `{name}`, `{index}`, and `{id}`. The index is one-based in request order. Use no evaluation, format specifications, attributes or conversions. Validate length, duplicate proposed names, case-insensitive collisions with existing names, and native prohibited characters before applying. A collision blocks the entire batch. No auto-name fallback or suffix is used. Use generated row keys in a review-only standard change preview.
3. For dependent copies, show the primary and every existing dependent affected by a template assignment. Revit synchronizes View Template across a dependent family. If the requested template differs, the plan requires explicit `allow_family_template_change` and includes every affected existing view and its ownership check. Show their before/after template, sheet placement, and controlled setting scope. If the requested template is already assigned, keep it and check the primary's ownership before adding a dependent. Use the real source/primary relation from Revit. Treat affected existing views and new views as distinct in the report. [Autodesk dependent view behavior](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-DocumentPresent/files/GUID-EF8CCDA0-9946-49FA-B7AB-2B94470525D2.htm)
4. Recompute the approved plan from a fresh read before both runs. Use `View.CanViewBeDuplicated` and `View.Duplicate` with the mapped enum. Use `IsValidViewTemplate` on each actual new view before assignment. Apply the shared dependent-family template only to the reviewed primary and verify every affected view has the expected template. Use one transaction. Regenerate and read back exact new IDs, UIDs, names, template IDs, view types and primary IDs. Compare existing family state and ownership. Fail atomically on a late conflict, failed API call or mismatch. Only roll back while Started. Treat Pending as unresolved and avoid document reads after regeneration failure. [Duplicate API](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/0cb1793f-1df0-d5b4-3b72-8d468b80199e.htm) · [Template assignment](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/2559f20b-87d4-e879-3139-7f555b251b71.htm)
5. Pass through the standard preview, ownership, dry run, Keep/Discard and post-run verification flow. Inspect the full telemetry. Match all new view IDs and disclose copied detail items and dependent view symbols. Autodesk documents that dependent sections, elevations and callouts can create a new symbol in the parent. Treat any additional or unexplained elements as review findings before real apply. Reread the unchanged baseline after dry run. On Keep read exact actual IDs and UIDs, including existing family/template state. On Discard prove baseline unchanged. Use a disposable Revit model with all three modes, Unicode exact names, an existing-name conflict, detail and dependent controls, and a differing dependent template with explicit family approval. Record the revision and native result before closing #143.

Limits and dependencies. Use up to 50 source views, 100 existing family members, a complete bounded name inventory, 2 MiB ASCII snapshot, and short read budgets. No new packages. Revit 2024–2026, pyRevit and a disposable project are needed for native validation. Undo one kept run to roll back the model and revert the merge to remove the recipe.

## Reviewed limits and handoffs

- Cap names at 100 characters and the pattern at 200. Scan no more than 10,000 view names, 20,000 viewports and 2,000 source detail elements, with a ten-second soft read limit and a 2 MiB ASCII payload. Bound actual additions to 2,000 view/detail/symbol elements and stop before committing on overflow. Resolve a template, actual recipient, and source element identities. Record exact template-controlled typed values and live source detail content. For each supported detail class, bind approval to its geometry, position, displayed content, type and relevant typed parameters and references. Record identity and version markers as additional evidence. Reject detailing for a source containing a class whose copied content cannot be represented completely. Refuse an incomplete snapshot. Test stale template values, an in-place unsaved move of an existing annotation with unchanged identity, and collector overflow. [Autodesk Element.VersionGuid semantics](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/2a1eae53-2c5c-a7be-1ef2-0f48626c62f5.htm)
- Substitute tokens in one pass. A brace inside a source name stays literal. Reject unknown, malformed or formatted tokens such as `{name:}`. Preserve Unicode and whitespace in valid names exactly. Use native IsValidName and exact readback. Do not auto-normalize names or insert fallback suffixes.
- Check `IsValidViewTemplate` on the actual assignment recipient and each actual duplicate. Use the shared template assignment only on the primary for a dependent family. Verify the primary and existing dependents after it runs. Use the ownership and model-update allowlist in focus_view.py:101–108. Recheck the primary immediately before dependent creation and all existing family members before template propagation. Include any reviewed existing outside-family target that native marker creation requires. A marker's containing view can differ from the dependency primary.
- Use the scripts workspace and keep the full get_run record with snapshot_json. Emit a machine plan and linked standard change-preview with `review_only: true`. Native apply consumes both, rejects blocking annotations, and compares immutable values to the recomputed plan. Preserve ownership annotations. Set ownership_ids to reviewed existing write targets and skip the ownership CLI when the list is empty.
- Reconcile every added, modified and deleted ID and every changed document in full dry-run telemetry. Classify additions as exact new view IDs, details owned by a new view, or a native dependent symbol tied to its actual new view. Show the symbol's containing view when it is outside the family. Reject incomplete telemetry and unexplained additions or modifications until the operator resolves scope and repeats the dry run. Verify that modified existing IDs are in the reviewed ownership scope. Block deletions and other-document edits. Test these controls and late rollback.
- Keep dry-run IDs provisional. Compare repeatable descriptors between runs. After approving the displayed preview, save full dry-run telemetry and reread the unchanged baseline. Check context and policy. Submit the same approved plan for Keep/Discard. Use baseline, side-effects and compare commands on complete envelopes. Verify the actual kept IDs, UIDs, view names, view templates and family relationships. After Discard compare the original baseline. Include a native dependent marker outside the family and a stale template or source annotation control in the acceptance receipt.
- In the native fixture, prove that a colliding name and a different family template without opt-in each reject before mutation. Force a late failure and exercise Discard separately, then compare each result to the original independent baseline. For approved Keep, verify exact new IDs, UIDs, options, names and templates, plus the template and placement of a pre-existing sheet-placed dependent. Record the tested revision, Revit version, fixture, dry-run and Keep/Discard receipts, and independent readbacks. Keep #143 open until those native checks are recorded.
