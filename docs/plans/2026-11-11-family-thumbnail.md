## Work order and recovery

1. Qualify the native path on disposable copies. Verify that the installed pyRevit Runtime supports family context and its Keep/Discard policy. Test an orthographic 3D view, a fixed isometric direction, shaded style, and a neutral background. Revit can reject [CreateIsometric](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/a913253d-2a92-b345-2b9a-882c1b152511.htm) even with a valid type. Record the rejection and rollback. Derive the target from visible solid geometry in a supported 3D view. Use the current family type and record it. Check families with multiple types and inspect the saved thumbnail. Verify which Revit versions support this path.
2. Enumerate the immediate source folder read-only. Bound one run to 250 entries, 25 selected RFAs, 128 MiB per file, and 512 MiB total. Require room for two copies of the batch and 256 MiB of additional free space. Report omitted entries and stop an over-budget batch. Resolve and verify disjoint local source, private staging, and output roots. Reject symlinks, reparse points, aliases, duplicate or existing output names, and external destinations. Treat a numbered suffix as a backup candidate. Let the operator choose whether to include it. Use the no-follow, exclusive creation, SHA-256 and space checks in the [batch model audit](../../skills/am-model-health/scripts/batch_model_audit.py) as the staging pattern. Preserve its RVT behavior. Revalidate the opened file identity and source hash before and after copying. Verify the staged byte hash. Never open a library source in Revit.
3. Classify every reviewed staged family before applying the batch. Record each supported 3D candidate, explicit unsupported reason, and unknown or unreadable case. Do not count a failed or unexamined candidate as unsupported. Limit each geometry scan to 2,000 elements and ten seconds between API calls. Stop and report incomplete coverage. Review one active staged family at a time. Bind reads and writes to the staged path identity, family identity, type, source hash and selected view. Compare the exact local snapshot before changing anything. Put a dedicated view in the preview. Use a known view UID from a prior receipt bound to that exact staged family lineage, or refuse an existing-name collision. Record non-workshared ownership explicitly. Do not infer workflow ownership from a name or the ownership report.
4. Reuse the standard change-preview renderer, side-effect helpers, and approval sequence from [focus-view](../../skills/am-safe-change/recipes/focus-view.md). Keep its project-only script separate. Recheck the active staged family and policy before each run. Check the dry-run status, intended added or changed view IDs, deletion count and other-document edits. Treat incomplete telemetry as unverified. Independently read the document preview setting. Requery the original snapshot after dry run to prove rollback. Under auto policy, obtain the second approval after the dry run. Use one transaction. Stop on stale state, wrong write scope, or wrong preview setting. Requery after Discard and confirm baseline. After Keep or an approved auto-policy commit, independently read the view, style, background, saved orientation and preview setting before saving. If the values differ, use Undo and recheck. Do not save on a mismatch or after Discard.
5. Open and activate the kept dedicated view in the staged family. Check the preview source and regeneration option in the Save As dialog. Save only to a new reviewed output path. Stop at an overwrite prompt. Hash the original again and record the output fingerprint. Keep separate outcomes for kept but unsaved, saved but unverified, verified, unsupported, refused, and failed. Resume verification only when the source hash, preset and output fingerprint match. If Save As was interrupted before a receipt was recorded, inspect the output and reconcile its identity or choose a new path. Keep any output with an unresolved conflict outside the verified set.
6. Reopen the output and verify the persistent view settings. Inspect its actual thumbnail in a fresh Revit process using [Load Family](https://help.autodesk.com/cloudhelp/2024/ENU/Revit-Model/files/GUID-2A6C26DE-63D7-48E8-A986-CAB6C362049A.htm) at the new output path. Compare the embedded thumbnail with the source when the stream is available. Use a contrasting orientation or color on a known asymmetric family, and include an unchanged control. Record Revit build, runtime and source revision. Require at least one supported 3D family and a verified output for every supported candidate. Keep #164 open while any candidate has unresolved eligibility. Report unsupported and unresolved candidates with distinct reasons. Preserve the sources so a wrong output can be set aside. Keep library replacement, global display preferences, automatic upgrades and geometry changes outside this workflow.

The [Autodesk developer note](https://blog.autodesk.io/rvt-and-rfa-thumbnail-image/) describes the storage mechanism. The sample files stay outside the repository.
- Test source and staged identity checks, aliases, collisions, no-op, cancellation, native rollback and interruption after saving. Include small and large 3D geometry, multiple types, a configured preview, an unrelated view with the same name, and an annotation-only control.
- Native evidence still requires a disposable Windows Revit host. Validate the camera, display style and thumbnail persistence with actual Keep and Discard runs. A passing fixture or offline suite alone does not establish that Revit saved the desired thumbnail.
